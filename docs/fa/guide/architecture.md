# معماری

## سه لایه

```
raw/       دست‌نخورده    ← شاهد
index.db   قابل بازسازی  ← بازیابی دقیق روی شاهد
wiki/      مشتق          ← تفسیر، با ارجاع به شاهد
```

| لایه | کِی خراب می‌شود | بازیابی |
|---|---|---|
| `raw/` | از دست رفتن دیسک | از بکاپ — هیچ راه دیگری نیست |
| `index.db` | خرابی، تغییر schema | حذف و بازسازی از `raw/` |
| `wiki/` | کهنگی، عدد غلط | خواندن دوبارهٔ `raw/`، اصلاح ارجاع |

چون `index.db` دورریختنی است، تغییر schema ارزان است. چون `wiki/` باید ارجاع
بدهد، عدد غلط پیدا می‌شود. چون `raw/` دست‌نخورده است، هر دو بازسازی می‌شوند.

## یک فایل در سیستم

```
contract-1405.pdf
      │  sha256، اندازه، مسیر
      ▼
files ──── ۱ ردیف
      │  file_id
      ▼
chunks ─── ۱۴ ردیف (text + fts_key + page)
      │  rowid
      ▼
chunks_fts ── فقط ایندکس معکوس، بدون کپی متن
```

`chunks_fts` یک جدول FTS5 با محتوای خارجی است: `content='chunks'`،
`content_rowid='rowid'`. متنی ذخیره نمی‌کند، پس باید با سه تریگر
(`chunks_ai`، `chunks_ad`، `chunks_au`) همگام بماند. اگر تریگرها را دور بزنی،
ایندکس بی‌صدا از متن جدا می‌شود — بدون خطا، جستجو فقط نتیجه نمی‌دهد.

## نرمال‌سازی فارسی

دو تابع، دو هدف:

| تابع | خروجی | کجا استفاده می‌شود |
|---|---|---|
| `normalize()` | `تأخیر` → `تاخیر`، `۴۸۰` → `480`، نیم‌فاصله → فاصله | `chunks.text`، چیزی که کاربر می‌خواند |
| `match_fold()` | همچنین `آ/أ/إ/ا` → `ا`، نقطه‌گذاری → فاصله | `chunks.fts_key`، چیزی که FTS5 ایندکس می‌کند |

اگر یک‌بار و تهاجمی نرمال کنیم، متن نمایشی خراب می‌شود. دو ستون هزینه‌اش یک
رشتهٔ اضافه به‌ازای هر تکه است.

چیزی که نرمال‌سازی حل **نمی‌کند**: مترادف (`جریمه`/`penalty`)، ریشه‌یابی
(`قرارداد`/`قراردادها` — با تطبیق پیشوندی حل می‌شود)، و املای متفاوت با حروف
مختلف (`بلیت`/`بلیط`).

## مسیر کوئری

```
query ──match_fold()──► توکن‌ها ──"a"* AND "b"*──► FTS5 MATCH
                                                        │
                                            join chunks, files
                                                        │
                                      فایل · صفحه/تکه · متن اصلی
```

کوئری از همان `match_fold()` عبور می‌کند که اسناد. تنها دلیل اینکه «تأخیر»
«تاخیر» را پیدا می‌کند همین است.

## ویکی هم ایندکس می‌شود

صفحهٔ ویکی یک منبع مثل بقیه است. بعد از نوشتن
`wiki/sources/contract-1405.md`، رویش `add` بزن:

```bash
python3 ~/archive/doclib.py add \
  ~/archive/collections/office-works/wiki/sources/contract-1405.md -c office-works
```

`rel_path` آن می‌شود `wiki/sources/contract-1405.md` — شاخهٔ دوم `rel_path_of()`
که هر چیزی داخل مجموعه را نسبی به ریشهٔ مجموعه ذخیره می‌کند. بدون این مرحله
صفحه در `search` پیدا نمی‌شود و هیچ‌چیز هشدار نمی‌دهد: `lint` ساختار را چک
می‌کند، نه قابل‌جستجو بودن را.

چرا ویکی را ایندکس کنیم؟ چون دو مسیر باید همدیگر را تقویت کنند. جستجوی یک
اصطلاح باید هم شاهد را نشان دهد و هم تفسیرش را — وگرنه قرارداد را می‌خوانی و
هرگز نمی‌فهمی صفحه‌ای در ویکی قبلاً تناقضی در آن دیده است.

## غیراهداف

بدون embedding، بدون جستجوی برداری، بدون OCR محلی، بدون رابط گرافیکی،
بدون چندکاربره، بدون تولید خودکار ویکی. هر کدام در این فهرست است چون اضافه
کردنش طراحی را عوض می‌کند نه اینکه آن را گسترش دهد.
